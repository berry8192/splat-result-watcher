# スプラのリザルト認識アプリ ⇔ nicomment の約束事

**この文書が正本**（2026-10-03 に nicomment から移した。約束事は出す側が持つ）。変えるときはこの文書だけを直し、
受け手に影響する変更なら nicomment に知らせる（nicomment 側が `splatoon_link.rs` を合わせる）。
「N Air の出力の撮り方」の節は nicomment もスプラと関係なく参照している（`nair_capture.rs`）ので、節の名前を変えるときは知らせる。

版: 0（2026-09-28）。受け手は [splatoon_link.rs](../../nicomment/app/src-tauri/src/splatoon_link.rs)、
送り方の見本は [examples/splat_detect_mock.rs](../../nicomment/app/src-tauri/examples/splat_detect_mock.rs)。

## 役割
- **認識アプリ**: 配信ソフト（N Air）の出力を 0.5 秒ごとに撮り（撮り方は下の「N Air の出力の撮り方」）、
  見本との照合で画面を読む。
  出すのは**事実だけ**（どの試合がどのルールで始まり、勝ったか負けたか、パワーはいくつか）。
  GUI で段階・撮影プレビュー・検出した試合の一覧・見本の登録を見せる
- **nicomment**: 受けた事実をセットの勝敗数・ルール別累積・パワーに反映し（`record_match`）、
  配信画面とキャラの声掛けに使う。解釈はこちらだけが持つ（両方で集計すると正が 2 つになる）

## バトルに有利になる情報は出さない
対人ゲームでのツール利用にあたるため、これは約束事の一部として守る。
- 試合中に出してよいのは `status`（段階）と `battle_started`（ルールと時刻）だけ
- それ以外の出来事は、勝敗の画面が出たあとに出す
- 相手の名前・ブキ・パワーは出さない

## N Air の出力の撮り方
約束事ではなく、認識アプリを作るときの手引き。2026-10-03 に N Air 1.1.20260909-1 で実機確認した。
**N Air の窓の配置や操作に左右されずに、配信に流れる絵そのものを 1920×1080 で撮れる**。

1. **N Air の操作口につなぐ**。N Air は名前付きパイプ `\\.\pipe\n-air-app` で内部の機能を
   JSON-RPC として出している（Streamlabs OBS 由来）。**トークンは要らず、既定で開いている**
   （WebSocket の口 59650 は既定で閉じているので使わない）。1 行 1 要求で、改行で締める:
   ```json
   {"jsonrpc":"2.0","id":1,"method":"createProjector","params":{"resource":"ProjectorService","args":[]}}
   ```
   合成済みの画像を返す口（obs-websocket の `GetSourceScreenshot` に当たるもの）は**無い**ので、
   次の手で窓を作って撮る
2. **出力のプロジェクターを開く**（上の要求）。N Air の子プロセスに、タイトル「全画面表示」・
   クラス `Chrome_WidgetWin_1` の窓が開く。中の子窓 `SlobsChildWindowPreview`（クラス
   `Win32DisplayClass`）に配信の出力が描かれる
3. **大きさを決めてから、窓を画面の外へ移す**。`SetWindowPos` で x=-8000 などへ逃がしても
   描画は止まらない。窓を **1920×1176** にすると、上の 96px が窓枠で子窓がちょうど 1920×1080 になる
   （`SetProcessDPIAware` を先に呼んでおく。このPCは表示倍率 150%。幅は丸めで子窓が 1px 大きく
   なることがあるので、窓枠の厚みは窓と子窓の差から測る）。
   **順番が大事**: 隠れている窓（画面の外・ほかの窓の下）では Chromium が中身の大きさを更新しない
   ので、画面の外で大きさを変えても子窓は追従しない。開いた窓がほかの窓の下に出ると、子窓は既定の
   960×504 のまま生まれる。Chromium は一部でも見えていれば「見えている」とみなすので、
   **最前面（`HWND_TOPMOST`）にして主モニタの左上に角を 8px だけ出し**、子窓が狙った大きさに
   なってから画面の外へ移して最前面を外す（2026-10-03 に確認。splat-result-watcher の `nair.rs`）
4. **子窓を `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)` で撮る**。D3D で描く窓でも黒くならない

本体の窓のプレビュー（同じ `SlobsChildWindowPreview`）も撮れるが、**選択中のソースの枠と
ハンドルが写り込み**、大きさも N Air の窓の配置で変わるので使わない。

- **窓は消えうる**。N Air を再起動したとき、人が閉じたときに無くなるので、撮れなかったら
  2 から作り直す。窓ハンドルは覚えておき、`IsWindow` で生きているかを見る
- **ディスプレイが消えている間は開けない**。電源設定でディスプレイが自動で消えると、全部の窓が隠れた扱いになり、
  新しく開いたプロジェクターの子窓が狙った大きさにならない（2026-10-03 に確認。自動で消える設定を切って直った）。
  開いた後にディスプレイが消えたときに撮れ続けるかは、まだ確かめていない
- **開いたまま放っておかない**。認識アプリを終えるときは `WM_CLOSE` で閉じる（画面の外にあるので
  人には閉じられない）
- プロジェクターは出力をもう 1 枚描き続けるので、GPU を少し食う。照合に 1920×1080 が要らないなら
  小さく開いてよい（大きさは上の 3 の手順で決める）。`PrintWindow` の時間は面積にほぼ比例する:
  1920×1080 で 25〜33ms、1280×720 で 12〜17ms、960×540 で約 16ms（このPC、release ビルド）
- **nicomment も同じ方法で撮る**（AI に配信画面を見せる。`nair_capture.rs`）。どちらも自分で開いた窓だけを
  撮り、相手の窓は触らない。`createProjector` は `null` を返して窓を教えてくれず、タイトルも同じなので、
  **開く前と後で「全画面表示」の窓を列挙し、増えた 1 枚を自分のものとして控える**

### OBS Studio のとき
OBS には obs-websocket（v5。OBS 28 から同梱）があるので、窓を作らずに済む（`src/obs.rs`）。
1. 利用者は OBS の「ツール → WebSocket サーバー設定」で有効にし、番号（既定 4455）とパスワードを認識アプリの設定に入れる
2. `ws://127.0.0.1:4455` につなぎ、`Hello` の `authentication`（`salt`・`challenge`）があれば
   `base64(sha256(base64(sha256(password + salt)) + challenge))` で `Identify`（`eventSubscriptions: 0`）
3. 0.5 秒ごとに `GetCurrentProgramScene` → `GetSourceScreenshot`（そのシーン名、`png`、`imageWidth`×`imageHeight` は撮る幅×16:9）。
   合成済みのプログラム出力が base64 の data URI で返る。OBS はキャンバスをその大きさに縮めるので、キャンバスは 16:9 にしておく
4. ゲーム穴の位置の約束（左詰め・16:9・上下の帯）は N Air のときと同じ

認識アプリの設定「撮る配信ソフト」が auto なら N Air を先に試し、無ければ OBS につなぐ（2026-10-06 から）。

## つなぎ方
- 認識アプリが WebSocket のサーバ、使う側がクライアント。既定は `ws://127.0.0.1:3140/events`
- クライアントは `?after=<最後に受けた seq>` を付けてつなぐ。サーバは次の順で送る:
  1. `hello`
  2. `seq > after` の出来事を古い順にすべて
  3. 今の `status`
  4. 以降は起きた順に流す
- サーバは**少なくとも 5 秒ごとに `status` を送る**。クライアントは 15 秒何も来なければ切れたとみなし、
  3 秒後につなぎ直す
- 文字列はすべて UTF-8 の JSON。1 フレームに 1 つの出来事

## 取りこぼしと二重計上
- `seq` は出来事ごとの通し番号。**認識アプリを再起動しても戻さない**（ファイルに控える）。
  記録を作り直して戻ったときは、`hello.last_seq` がクライアントの控えより小さくなるので、
  クライアントは 0 からつなぎ直す
- **正しさは `match_id` が担う**。同じ試合の出来事は何度届いても 1 回しか数えない
  （nicomment は `splatoon_matches.match_key` に控える）。`seq` は再送の量を減らすためのもの
- nicomment は、30 分より前に終わった試合の再送を数えない（前の配信の試合を今のセットに積まないため）

## 出来事
時刻はすべて RFC 3339（UTC）。モードは `x` / `bankara_challenge` / `bankara_open` / `other`、
ルールは `area` / `yagura` / `hoko` / `asari` / `turf_war`（ナワバリバトル。モードは `other`）。分からない項目は省くか `null`。

### `hello`（seq なし）
```json
{"type":"hello","app":"splat-result-watcher","version":"0.1.0","last_seq":42}
```

### `status`（seq なし）
```json
{"type":"status","state":"in_battle"}
```
`state`: `no_signal`（映像が取れない）/ `idle` / `in_battle` / `reading` / `post_match`。
nicomment は `in_battle` の間、AI に画面を見せない（設定 `screen_view.in_battle` で外せるが既定は見せない）。
これとは別に放送者が対戦に入るときに手で切るスイッチ（`screen_view.enabled`）があり、認識アプリが
つながっていない日はそちらが受ける。

### `battle_started`
```json
{"seq":43,"type":"battle_started","match_id":"20260928-2104-01","at":"...","mode":"x","rule":"hoko"}
```
`rule` は**試合を始めたときのルール**。ローテの切り替わりを跨いだ試合は、切り替わる前のルールで
数えるためにここで決める（あとからスケジュールを引いても、終わった枠はもう返ってこない）。

### `result`
```json
{"seq":44,"type":"result","match_id":"20260928-2104-01","outcome":"win",
 "mode":"x","rule":"hoko","started_at":"...","ended_at":"..."}
```
**`started_at` は必ず送る**（声で付けた記録との突き合わせに使う。下の「手で付けた記録との突き合わせ」）。
`outcome`:
- `win` / `lose`
- `no_contest`: 無効試合（試合開始直後の切断で DRAW になりロビーへ戻る）。数えない
- `lose_uncounted`: 試合の途中で誰かが切断し、人数の少ない側が負けたとき。LOSE の表示に
  「負けとしてカウントされませんでした」が付く。**セットの負け数にもウデマエポイントにも入らない**ので
  数えない。文言の有無で `lose` と見分ける（終盤の切断や自分の切断は普通の `lose`）

`mode` が `other`（ナワバリ・イベント・プラベ・フェス）なら数えない。フェスの本祭の間は X もバンカラも
開かれない。`other` の試合も `battle_started` / `result` は流す（試合の区切りとして。2026-10-06 から。
それまでは `result` を出していなかった）。ナワバリは紹介で分かるので `battle_started` に `"mode":"other","rule":"turf_war"` が付く。
`rule` が無ければ nicomment は `battle_started` のルール → `started_at` 時点のスケジュールの順で補う。

### `power`
```json
{"seq":45,"type":"power","match_id":"20260928-2104-01","kind":"x","rule":"hoko",
 "before":1938.5,"after":1983.5,"calibrating":false,"at":"..."}
```
`kind`:
- `x`: X パワー。`rule` はそのセットのルール（X のセットはルールごと。下の「X のセット」）。計測中
  （ルールごと・シーズンごとに最初の 5 戦）は `calibrating: true` で `after` を省く。計測中の `power` には、
  分かればそのルールの計測中の勝敗の並び `calibration`（例 `["win","lose","win"]`）を付ける（省いてよい。
  計測中の画面は「3/5」と出るだけで並びは出ないので、付けるなら記録した `result` から作る。2026-10-03 時点で
  認識アプリはまだ付けない）
- `udemae`: **ウデマエポイント**（バンカラ共通）。チャレンジは終えたときにまとめて精算され、
  オープンは 1 試合ごとに動く。バンカラパワー（グループで参加したときだけ測られる）は扱わない。
  昇格でポイントがリセットされたときは `before: null`・`after: 300`（「昇格おめでとう」自体は出さない）

nicomment は推定値（X セット完了の増減表・オープンの勝ち +20 / 負けは帯ごとの表）を**画面の値で上書きする**。
公式の X の増減表は「最小幅」で、計測の直後などは 100 以上動く。
値の大きさでは弾かない（150 以上動くこともある）。読み取りの確かさは認識アプリ側で保証する
（1 文字ずつの一致度・形式・数フレームの安定）。

**`power` が来たら、nicomment はそのセットを締めて 0-0 から数え直す**（X のセット完了・バンカラチャレンジの精算。
2026-10-03 のユーザー判断）。ポイントが動くのはゲームの中でセットが終わったときだけなので、勝敗を 1 つ読み落として
2-1 のまま止まっていてもゲームに揃う。締めるのは今のセットがそのポイントのもの（X は同じルール）のときだけで、
`match_id` の試合より後にもう記録があれば締めない。オープンはセットが無いので締めない。勝敗の読み間違いは
nicomment の設定画面で手で直す。

**同じ試合の `result` は、必ずその試合の `power` より先に送る**（2026-10-03 に決めた）。nicomment は `power` で
セットを締めるので、逆になると締めた後でその試合の勝敗が届き、新しいセットの 1 戦目として数えてしまう。
認識アプリは `result` を出してからでないと試合後の画面（パワー・精算）を読まない。見出しを見落として X パワーや
精算の画面からモードを補うときも、同じフレームで `result` を先に出す（試験 `result_comes_before_power_of_the_same_match`）。

### `set_progress`
```json
{"seq":46,"type":"set_progress","match_id":"20260928-2104-01","wins":2,"losses":1}
```
版 0 の nicomment は控えるだけ（勝敗の読み間違いは手で直すと決めたので、当面これで記録を直すことはしない）。

### `observed`（試合と結び付かない、今見えた自分の値）
```json
{"seq":47,"type":"observed","kind":"x","rule":"hoko","value":1983.5,"wins":1,"losses":0,"at":"..."}
```
- 出す画面: ロビーのメニューとマッチング中の画面（自分の X パワー・ウデマエポイント・進行）、バンカラの参加費の画面
  （支払う前の値＝そのチャレンジを始めたときのウデマエポイント。`kind: "udemae"`）
- `kind` は `power` と同じ（`x` / `udemae`）。`value` は X なら 0.1 刻みの数、ウデマエなら整数（マイナスもある）。
  `rule` は X のとき（X パワーはルールごと）。`wins` / `losses` は進行が見えたときだけ。`match_id` は付けない。
  メニューの値の字がまだ読めず、勝ち負けのランプだけ見えたときは `value` を省く（2026-10-06 から）
- `rank` は `kind: "udemae"` のとき、メニューの「S+1 284p」から読めたウデマエのランク（`"C-"`〜`"A+"`、`"S"`、`"S+0"`〜`"S+50"`。2026-10-06 から）。
  英字は字の左右の埋まり方で、S+ の数字はメニューの数字の見本で読む。決まらなければ省く（S・S+ は本番で確かめた。A・B・C は見本が無く未確認）
- 同じ値を続けて出さない（値・進行・ランクが変わったときだけ）
- nicomment は値が食い違えば直すだけで、**セットは締めない**
- 試合中は出さない（自分の値なのでバトルに有利になる情報ではないが、試合中に出すのは `status` と `battle_started` だけ）
- 2026-10-03 時点で認識アプリはまだ出さない（メニューの値は色つきの字なので、読む工夫と見本が要る）

### `lobby`（ロビーのメニューで選んでいるモードとルール）
```json
{"seq":48,"type":"lobby","mode":"bankara_open","rule":"asari","at":"..."}
```
- 出す画面: ロビーのメニュー（左の大きなカードと、右下の「ルール」欄）。2026-10-06 から
- `mode` は `x` / `bankara_challenge` / `bankara_open` / `other`（レギュラーマッチ。`rule` は `turf_war`）。
  イベントマッチなど、ほかのカードでは出さない。`rule` は読めたときだけ出すので、`lobby` には必ず付く
- 選択が変わって落ち着いたときに 1 回だけ出す。試合を始めると忘れるので、試合の後にメニューへ戻れば同じ選択でも出し直す
- 試合中は出さない
- メニューで X パワーが読めたときの `observed` には、ここで読んだルールが `rule` として付く
- マッチングの画面が映らなかった試合（オープンなど）の `battle_started` の `mode` は、直前に `lobby` で出したモードで補う（ルールが同じときだけ）
- 受け手は、表示するモードとルールを切り替える手がかりにする（値や勝敗の集計には使わない）

### `manual`（手で直した値）
```json
{"seq":48,"type":"manual","kind":"x","rule":"hoko","value":2250.0,"wins":2,"losses":1,"at":"..."}
```
- 認識アプリの設定ウィンドウの「手動操作」で、放送者が手で直した値。**差分ではなく直した後の値**（冪等。何度届いても同じ結果）
- `kind` は `x` / `udemae`。`value` はパワーまたはウデマエポイント（省略されることがある）。`wins` / `losses` は現在のセットの勝敗数（省略されることがある）。`rule` は X のとき。`match_id` は付けない
- 受信側は、付いている項目だけをその値で上書きする（セットは締めない）。無視してもよい
- 試合中でも送られ得る（放送者自身の操作で、自分の値なのでバトルに有利になる情報ではない）

## X のセット
X マッチの「3 勝か 3 敗まで」は**ルールごと**に数えられる。ローテが変わって途中になったセットは、
そのルールのところで保留になり、次にそのルールが来たときに続きから再開する。nicomment は今のルールの
セットを表示し、ほかのルールの途中のセットを預けておく。`battle_started` / `result` の `rule` は、
どのルールのセットに数えるかを決めるのにも使うので、読めるなら必ず送る。

シーズンの切り替え（3・6・9・12 月の 1 日 9 時）やウデマエのリセットで、X の途中のセットと
チャレンジの途中経過は消える。頻度が低いので、nicomment は設定画面のボタンで手で捨てる。

## 手で付けた記録との突き合わせ
**時間の幅では突き合わせない**。回線落ちなら試合は 45 秒ほどで終わるので、「3 分以内なら同じ試合」の
ような幅はどう取っても別の試合を拾い得る。代わりに `battle_started` / `result` が作る**試合の区切り**を使う。

画面の `result` が来たとき:
- その試合の**開始（`started_at`）より後に**声で付けた記録があれば、同じ試合とみなす
  （開始より前に付けたものは前の試合のこと）。いちばん新しい行が声の記録のときだけ
  - 勝敗が同じ → 声の記録に `match_id` を結び付け、数え直さない
  - 勝敗が違う → 声の記録を取り消し、画面の方で付け直す

**つながっている間は、声では記録しない**（nicomment は AI に勝敗記録のツールを渡さない）。
声の操作は補助で、最終的には使わずに済むようにする。上の突き合わせが効くのは、切れていた間
（nicomment の入れ替え中・認識アプリが止まっていた間）に声で付けた記録だけ。
設定画面のボタンは対象外（読み違いや付け忘れを手で直すため）。
