# 設計の方針（2026-09-28〜10-03、nicomment のセッションで決めたこと）

nicomment との約束事は [protocol.md](protocol.md)。**この repo の protocol.md が正本**（2026-10-03 に nicomment から移した）。
受け手に影響する変更をしたら nicomment に知らせる（受け手は nicomment の `splatoon_link.rs`）。

## 何を作るか
スプラトゥーン3 の配信映像からリザルト画面を読み、X マッチ／バンカラマッチの勝敗・X パワー・
ウデマエポイントを WebSocket で流す、**単独で動くアプリ**。GUI で見せるのが主で、作り込む人は
localhost の WebSocket で受ける。nicomment はその受け手の 1 つ。

- nicomment に同居させない理由: 0.5 秒ごとの撮影と照合が固まっても読み上げを道連れにしない／
  nicomment の入れ替え（live-swap）の数秒も認識を止めない／nicomment を使わない人にも使える
- 当面は**非公開**。自分の配信で安定してから公開を考える。言語は **Rust の単一 exe（GUI は Tauri）** の案
  （配る相手に Python の環境を要求しない。撮影と照合は `windows` / `image` で書ける）

## 決まっていること（ユーザーの判断）
- **バトルに有利になる情報を出さない**（対人戦でのツール利用にあたるため）。ガードは出力側で効かせる。
  試合中に出すのは `status` と `battle_started`（ルールと時刻）だけ。試合中の値（カウント・時間・
  スペシャル・相手の位置）に ROI を置かない。相手の名前・ブキ・パワーは読まない・残さない・出さない
- **撮影は 0.5 秒ごと**。1 回の撮影が重ければ（目安 20ms 超）1 fps に落とす
- **認識に LLM を使わない**。見本（テンプレート）との照合だけで読む。色はチームごとに変わるので、
  白い文字の形（白に近い画素だけ残した 2 値）で比べる
- **ゲームの音は使わない**。取れるのは配信の音（放送者の声・キャラの読み上げ・BGM が混ざる）で厳しい
- **映像は N Air 経由**（キャプボは 1 アプリしか掴めない）。撮り方は protocol.md の「N Air の出力の撮り方」
  （名前付きパイプでプロジェクターを開き、画面外に置いて PrintWindow。2026-10-03 に実機確認済）
- **パワーの値の大きさでは弾かない**（150 以上動くことがある）。確かさは次で保証する:
  1 文字ずつの一致度がしきい値を超える／形式（整数 3〜4 桁＋小数 1 桁）／同じ値が 3 フレーム続く
  （数え上がる演出への備え）／画面に前の値や増減も出ていれば計算が合う
- 見本は**各自の画面から GUI で登録**する形が安全（ゲーム画面の切り抜きを同梱するのは任天堂の
  ガイドラインの対象外）。数字は 0-9 と小数点の見本を切り出して手でラベルを付ける道具を用意する
- 試合後の分析（カウントの推移・キルデス）は将来。試合中は読むだけで出力せず、結果が出てから話す形なら
  録画の見返しと同じ構造。そのとき改めて判断する

## 撮った絵について（2026-10-03 に実機で確認）
- 撮れるのは**配信の合成画面**で、ゲームの映像はその一部にすぎない（周りに配信の飾り・コメント・
  立ち絵・nicomment の X パワー表示が乗る）。照合はゲーム穴を切り出してから行う。
  配信の飾りに出ている X パワーなどを読んではいけない
- **スプラの配信では画面の配置を変えないので、ゲーム穴は固定の矩形で持つ**（ユーザー判断 2026-10-03。
  合わせる GUI は作らない）。nicomment のスプラのテーマ（上帯 10%・下帯 10%・16:9・左詰め）から
  1920×1080 の出力の中で **x 0, y 108, 1536×864**。撮った出力の黄色い枠とも合う（`src/layout.rs`）。
  枠は縁に数 px 重なるので、ROI は縁に寄せすぎない
- 撮る大きさは `PrintWindow` の時間で決める（面積にほぼ比例。1920×1080 で 25〜33ms、
  1280×720 で 12〜17ms）。20ms を超えると 1 秒ごとに落とす決まりなので、**1280×720 で撮る**のを
  既定にする。1280×720 で撮るとゲーム穴はちょうど 1024×576。数字の照合に足りるかは見本で確かめる

  - [x] 設定（`settings.json`: 待ち受けの番号・撮る幅・録画の入り切りと上限）、見本のそろい具合（見せる窓にも出す）、

## 試合の管理（2026-10-03 に「読めた事実を積む」形に作り直した。`src/state.rs`）
決まった順番の状態遷移には頼らない（見落としがあると引っかかるため。ユーザー判断）。「今の試合」1 つに、
読めた事実を順不同で積み、そろったものから出す。今の試合を持つ理由: 出来事を `match_id` でまとめる・
試合中は status と battle_started しか出さない・戦績の見返しを数えない・`started_at` を送る。
- **試合はルール紹介から始まる**（試合は必ずそこから始まる。ユーザー判断）。紹介を見たらいつでも新しい試合を
  始め、前の試合はそろった分を出して閉じる（見出しを読めないまま次の試合に進んでも引っかからない）。
  紹介は回線によって 1 分近く続くことがある（ユーザー情報）。途切れても 10 秒以内にまた読めれば同じ一続きとみなし、
  一続きにつき試合は 1 つ。マッチング待ち（15〜180 秒）はロビーなので試合の外
- 紹介を見落としたときは、**30 秒以上ぶりに映った勝敗の画面**で試合を始める（`started_at` は勝敗を見た時刻）。
  30 秒以内にまた映った勝敗の画面（ロビーでの戦績の見返し）は数えない
- **`result` は勝敗とモードがそろったら出す**。モードは個人リザルトの見出しのほか、X パワーの画面が読めたら X、
  バンカラの精算が読めたらチャレンジとして補う。モードが「その他」なら出さない。見出しの「無効試合になりました」
  だけでも無効試合として出す。試合が無いときの見出し（ロビーでの見返し）は使わない
- **マッチング中の画面**（左のパネルの「Xパワー」「ウデマエ」）でモードを読み、紹介の直前（60 秒以内）まで見ていたら
  その試合に持たせる（`battle_started` に `mode` が載る）。マッチングをやめて別のモードに行ったときは持ち越さない。
  **WIN は勝敗が読めた時点で出す**。**LOSE は見出しを待つ**（「負けとしてカウントされませんでした」が付くかもしれない）。
  見出しを見落としたまま次の試合・時間切れになったら、マッチングのモードで lose を出す。
  メニューを開いていないときのマッチング画面は表記が違うはずなので、ユーザーが確かめる（2026-10-03）
- バンカラの精算（挑戦終了!／勝ちぬけ!）はゲージの下の今のポイントと TOTAL を読む。昇格（昇格おめでとう!!）は
  リセットの 300p を `power`（udemae, before なし）で出し、「おめでとう」自体は出さない（ユーザー判断）
- パワー・進行は `result` の後に読み、それぞれ 1 試合 1 回（「途中の値を拾わない」）
- **今の試合は `%LOCALAPPDATA%\splat-result-watcher\current_game.json` に控える**（変わったときだけ書く）。落ちても
  リザルトまでに起動し直せば続きから読む（ユーザー判断）。読み戻すときも下の時間切れを当てはめ、古ければ捨てる
- 見失った試合を閉じる: 勝敗が来ないまま 15 分／勝敗からモードが分からないまま 120 秒（出さない）／
  `result` の後に何も読めないまま 180 秒
- 段階（`status`）は積んだ事実から決める: 試合が無い → idle、勝敗がまだ → in_battle、勝敗はあるがモードがまだ →
  reading、`result` の後 → post_match。映像の無いフレームが 4 つ続けば no_signal（試合は持ったまま）
- 勝敗は先に出し、パワーは後から出す（勝敗の画面が先に来るので配信画面がすぐ動く）
- ロビーの精算は A 長押しで早送りできるので、パワーの画面は短いことがある。読めなければ出さない
  （nicomment が推定値のまま残す）

## 数字の読み方で分かったこと（2026-10-03）
- 低いかたまり（行の高さの 5 割未満）は見本と比べずに形で決める。真ん中が行の 7 割より下なら小数点、上ならマイナス
  （小さい字では小数点も横に長くなるので、形ではなく高さの位置で分ける）。TOTAL の前の「=」もマイナス扱いになるので、
  TOTAL では先頭のそれを捨てる
- 「130p」の p は最後のかたまりとして捨てる。切り抜きの右端に数字以外の白いもの（パネルの縁）が入ると p が残るので、
  右端は数字の終わりのすぐ外にする
- 精算のゲージの下の字は細く、照合する大きさ（1024 幅）では線が 1px ほど。しきい値 200 では途切れ、150 では字がくっつく。
  165 で手元の見本は通るが、ぎりぎり。確かさは「今のポイント＋TOTAL」の計算で守る
- TOTAL の数字は X パワーの数字と字体が少し違い、X パワーの見本では一致度 0.8 止まりだった。見本の種類を分けた

## ゲームの仕様で気をつけること（2026-09-28 に Web で確認。任天堂の更新データ 〜Ver.11.3.0）
- X のセットは**ルールごと**。ローテで途中になったセットは保留され、次にそのルールが来たら続きから
- X の計測はルールごと・シーズンごとに最初の 5 戦。シーズンの切り替え（3・6・9・12 月の 1 日 9 時）や
  ウデマエのリセットで計測に戻る
- 公式の X の増減表は**最小幅**（計測直後は −117 のように超える）
- ソロのオープンに「パワー」は無い（バンカラパワーはグループ参加時だけ）。動くのはウデマエポイント
- 開始直後の切断は DRAW の無効試合（その期間は Ver.11.2.0 で短縮）。途中の切断で人数の少ない側が
  負けると LOSE ＋「負けとしてカウントされませんでした」。終盤の切断と自分の切断は普通の負け
- フェスの本祭の間は X もバンカラも無い。イベントマッチは別のパワー
- リザルトの演出（30〜40 秒）はスキップできない。X の試合中の名前はコールサイン

## ランクマッチの仕様（2026-10-03 に Web で調べた。主な出典は下）
出典: wikiwiki.jp/splatoon3mix の「バンカラマッチ」（2026-06-30 更新）・「Xマッチ」（2026-09-30 更新）・「オンライン対戦」、
任天堂の更新データ（support.nintendo.com/jp/switch/software_support/av5ja/ の 920・1000・1110・1120・1130）。Inkipedia は読めなかった。
- **チャレンジの参加費**: C- 0 / C 20 / C+ 40 / B- 55 / B 70 / B+ 85 / A- 110 / A 120 / A+ 130 / S 170 / S+ 180
- **チャレンジの精算**: TOTAL = 勝ち数 × 単価（C 20 / B 30 / A 40 / S・S+ 50）＋ 勝ち数ボーナス（2 勝 +5 / 3 勝 +15 /
  4 勝 +30 / 5 勝 +50）＋ 表彰（金 1 つ +5・銀 1 つ +1。負けた試合の表彰も入る）。手元の見本で合った:
  0 勝 3 敗で表彰が金 3・銀 5 → 25p、5 勝 2 敗（S）で表彰が金 15・銀 5 → 250 + 50 + 75 + 5 = 380p。
  「2連続!」（連続勝ちぬけ）は王冠の段階だけで、ポイントには入らない
- ウデマエポイントは −9999〜9999。マイナスでも降格しない
- **昇格戦**: S→S+0 は 1000p を超えると挑める（見本の 1051p と合う）。3 敗までに 3 勝で合格、失敗はポイント無し。
  合格で初期値に戻る（B- 100 / A- 200 / S・S+0 300）。S+ の中は 650 + 350k の線で自動で上がり、10 段ごとに 3800 で昇格戦
- **オープン**: 1 戦ごとに勝ち +20、負けは帯で −3 / −5 / −8 / −10 / −13（Ver.10.0.0 から）。参加費なし・表彰は関係しない
- **X**: S+0 以上で参加。X パワーは **500 より下がらない**。セット完了の増減の最小幅は 2500 未満で ±25 / 50 / 75
  （2500〜3000 は ±15 / 30 / 45、3000 以上は ±10 / 15 / 20）。計測直後などは 100 を超えて動く
- **シーズンの切り替え**（3・6・9・12 月 1 日 9:00）: チャレンジの途中も X の途中のセットもリセットされる（X のセットはユーザー情報）。
  ウデマエは過去最高から決まり、ポイントは初期値。X パワーは消えて全ルールが計測から
- ローテは 2 時間ごと、奇数時に切り替わる
- **負けとしてカウントされない試合は集計の対象外で、表彰の加算もない**（ユーザー情報。資料には明記が無かった）

### 仕様から取り入れた確かめ（2026-10-03 のユーザー判断）
- [x] 範囲で弾く: X パワーが 500 未満なら読み違い（`recognize.rs` の `X_POWER_MIN`）。ウデマエは 4 桁までに限るので −9999〜9999 に収まる
- [ ] **表彰の内訳を試合ごとに積む**: 各バトルの後の個人リザルト「ゲットした表彰」で金・銀を数えて今の試合に持ち、精算の前に
  TOTAL を計算しておく（読んだ TOTAL と合うか確かめる。負けとして数えない試合は積まない）。金と銀は色で見分ける照合が要る
- [ ] 参加費の確かめ: 参加費の画面の「支払う前 − 参加費 = 支払った後」をウデマエごとの額で確かめる（ウデマエも読む必要がある）
- [ ] オープン（対応するとき）: 1 戦ごとに +20 か帯ごとの負けの値で確かめる

## 見本集めで確かめること
1. 勝敗の画面・スコアボード・進行・パワーの画面が、どの順番で何秒ずつ出るか
2. モードとルールがどの画面のどこに出るか。ルールアイコンがバトル中も出ているか
3. X の計測中がどう見えるか
4. 無効試合・負けとして数えられない負けの画面
5. ボタン送りで飛ばされる画面があるか
6. バトル中と見分けられる安定した部分（上辺のカウント表示など。値は読まない）
7. ルールの切り替わりをまたいだバトル（めったに起きないので普段から撮り溜めて拾う）
8. パワーの数字が数え上がる演出があるか
9. 反応してはいけない画面: ナワバリ・イベント・プラベ・サーモンランのリザルト、ロビー、メニュー、
   ロード中、配信中に映した別の動画

### 途中の値を拾わない（2026-10-03 に方針を決めた）
UI はゆっくり出る。進行は勝った後も「1-1」がそこそこ長く出てから「2-1」に変わる。パワーはドラムロールのように数が動く。
1. **画面がそろうまで読まない**: 値を読む前に、その画面の決まった文字（「Xパワー」「WIN LOSE」「TOTAL」など）が
   十分に一致していることを同じフレームで確かめる。出てくる途中の薄い文字は 2 値で黒に落ちるので、一致しない
2. **最初ではなく、落ち着いた最後の値を取る**: 3 フレーム同じ値なら候補にし、画面が消えるまで上書きし続け、
   消えたとき（または一定時間たったとき）に出す。1-1 の後に 2-1 が来れば 2-1 になる
3. **計算が合わなければ出さない**: X パワーは旧値＋増減＝新値になった値だけ（合えばその時点で確定してよい）。
   バンカラの精算は今のポイント＋TOTAL。進行は WIN の判子の数と勝ち数が合い、いま終わった試合の勝敗とも合うときだけ。
   X の計測完了は確かめる材料が無いので 2. だけ。合わないまま終わったら何も出さない（nicomment は推定値のまま）
- A ボタンでの早送りはユーザーも試したことがなく、どうなるか分からない。配るなら「押さないで」と README に書く
- 秒数（1-1 の長さ・ドラムロールの長さ・3 フレームと一定時間の値）は `record` の録画で測って決める

### 集計のずれを後から直す（ユーザーの案。約束事の `observed` に足した。値を読む照合はまだ）
ロビーのメニューやマッチメイク中の画面に、自分の今の値が出ている（X なら「Xパワー : 2100.0」と進行の○、
バンカラなら「S 300p」と○の列。X の計測中は「計測中... 0/5」）。これを読んで nicomment の値と食い違えば直す。
試合と結び付かない「今見えた値」を流す出来事が要る（自分の値なので、バトルに有利になる情報には当たらない）

- まだ見本が無いもの: バンカラ（オープン）、個人リザルトでの「負けとしてカウントされませんでした」、
  試合中の画面、反応してはいけない画面（ナワバリ・サーモンランなど）。画面ごとの秒数は録画（`record`）で測る

## 公開するなら
- 入力は映像だけ。NSO / イカリング3 の API・Switch 本体には触れない（処分が報じられたのはそちら側）
- 試合中に何も出さないことを README に明記する（IkaLog は試合中にキル・デスを実況していた）
- 無料にする（splatoon3.ink の利用条件。任天堂のガイドラインも販売を禁じる）
- splatoon3.ink を使うなら User-Agent を付け、取得は 1 時間に 1 回以下、クレジットを表記する。
  終わった枠は返らないので、取得したものを手元に保存して突き合わせる
